# Android-to-Harmony Executable Planning Foundation

## Problem Statement

The reusable Android-to-Harmony migration workflow can inventory source artifacts and generate migration output, but it needs one trustworthy route from project facts to executable vertical slices. Ownership guesses, runtime-edge dependencies, stale identities, incomplete evidence, and standalone helper entry points make migration results difficult to reproduce and unsafe to treat as a complete Harmony application.

Batch 1 and Batch 2 of the prior planning change are implemented and verified. The remaining work must finish the foundation through small, project-backed tracer bullets instead of another monolithic execution batch.

## Solution

Keep one normal workflow entry that exposes the current immutable execution plan joined with mutable task state. Prove the full evidence path incrementally with three fixed public Android projects. Every tracer bullet must improve reusable Skill, Gate, Test, or evidence behavior and then verify it through the highest available public CLI seam.

## User Stories

1. As a migration operator, I want start, resume, and status to expose one current execution plan so that I do not need a second planner workflow.
2. As a migration operator, I want task readiness to remain bound to current plan and task-state identities so that stale work is never executed.
3. As a migration maintainer, I want standalone analyzers to remain debug-only so that normal users cannot bypass workflow gates.
4. As a migration maintainer, I want a portable Skill-tree identity so that evidence remains valid in another checkout.
5. As a migration maintainer, I want every evidence family content-bound so that missing, extra, or tampered artifacts fail closed.
6. As a migration maintainer, I want fixed-revision Banking evidence so that one complete public-project path proves the capture design.
7. As a migration maintainer, I want Ekspensify to exercise reuse and wrong-HEAD repair so that the helper is not tailored to Banking.
8. As a migration maintainer, I want Buckwheat to exercise clean acquisition and remote/revision rejection so that unsafe source state cannot be frozen.
9. As a project manager, I want the three project results aggregated into one portable evidence tree so that the foundation has reproducible completion evidence.
10. As a project manager, I want tests to distinguish business completion, Gate completeness, and evidence integrity from mere compilation success.

## Implementation Decisions

- The only normal user seam is the migration workflow agent; graph, gate, plan, hash, and capture helpers are internal maintainer seams.
- The execution plan is immutable and content-addressed; mutable lifecycle state points one-way to the plan identity.
- Runtime navigation, import, and call edges record provenance but never create implementation prerequisites.
- Evidence capture accepts structured source/project parameters and constructs fixed subprocess argument lists internally; arbitrary shell-command parameters are forbidden.
- Skill identity is owned once by the current effort. Project evidence refers to that central identity instead of duplicating it.
- Historical benchmark evidence remains read-only.
- Banking, Ekspensify, and Buckwheat use their already approved public URLs and fixed revisions.
- No commit, push, release, remote issue, or AI image/screenshot recognition is authorized.

## Testing Decisions

- Manager-approved public seams are: workflow start/resume/status, checked public-project capture, portable evidence-tree generate/verify, and repository-level workflow routing.
- Every changed behavior starts with a failing test at one of those seams, followed by the minimum implementation and the same test passing.
- Each public project is a tracer bullet that must produce a complete required evidence subtree, not merely a successful command exit.
- Missing source, wrong HEAD, wrong remote, final revision mismatch, missing evidence family, unexpected artifact, and tampering are fail-closed cases.
- Final regression reruns the complete Python and Node suites affected by the foundation.

## Out of Scope

- Migrating an additional production application.
- Claiming visual fidelity from build or static evidence.
- Changing Harmony UI generation behavior unrelated to executable planning.
- Reopening historical benchmark evidence.
- Publishing or committing the work.

## Further Notes

The prior Spec Superflow artifacts remain reference material and an evidence location. From this point, the local Matt tickets and their blocking graph govern implementation order. The project manager owns intermediate ticket acceptance; the user is asked only for final project acceptance or a genuine external blocker.
