# Typed UI and dependency continuation

This increment continues the four compiler lanes. It does not add page-specific
rules or claim that the entire Kotlin language or Compose framework is supported.
Review, commit/push and native visual acceptance are outside this batch.

## Representation change

```text
Official resolved Kotlin IR
  -> checked source/binary bodies and verified common lowering
  -> language lowering + resolved framework/library rules
  -> EtsProgram (ordinary code and UI)
  -> shared validator and dependency traversal
  -> shared ETS printer
```

`ComposeLowering.lower` returns this same program. The removed `UiTextModule`
was an intermediate text envelope, not an acceptable typed target contract.
No raw-source node replaces it. Controls and ordered modifier boundaries are
`EtsUiElement`; content iteration is `EtsUiForEach`. Conditions, expressions,
callbacks and local-value semantics reuse the existing language nodes. Component,
builder/build and reactive-state metadata belong to declarations. Record-shaped
API arguments have field types and recursively checked values.

The shared printer alone writes ArkUI DSL. The adapter does not load the printer,
join source lines, parse output, select a preview branch or implement its own
general expression formatter. Necessary WrappedBuilder and evaluate-once bridges
remain typed declarations; this change does not pretend those platform bridges
disappeared or broaden the supported callback/slot forms.

Fixed typography and touch-arbitration code remains platform runtime support.
`ComposeRuntime` selects only referenced, signature-checked owned helpers and
composes `StandardLibraryRuntime`. Fixed library implementation text is distinct
from dynamically generated page source. It is not a second UI output route.

## Other lanes

- Binary bodies: real Kotlin 2.1.20 serialized JVM inline bodies, actual
  SourceFile provenance, canonical symbol linking and official inlining. See
  [binary-bodies.md](binary-bodies.md) for the bounded file-facade subset and
  unsupported dependency graphs.
- Loop lowering: official loop passes plus substitution of generated generic
  call result types using official type identities. Existing source calls and
  source positions are retained. See [loops.md](loops.md).
- Runtime: array/list/iterator/progression protocol implementations are selected
  by resolved identities. Runtime types carry explicit external identities;
  cross-file cursor values retain shared mutable position through closures,
  without confusing source classes or materializing entire ranges.

These are implementations behind the existing shared contracts, not four
independent parsers or four ways to generate ETS expressions.

## Verification boundaries

- `tests/ui/target-contract.sh`: target nodes compile independently; validates
  calls, records, UI branch/item types, rejects UI DSL inside an ordinary callback.
- `tests/ui/typed-program.sh`: actual K2 IR to UI target tree with Printer.kt,
  Main.kt and output code absent. Checks source symbols, slots, state reads/writes,
  pager effects, target traversal and fixed runtime dependency signatures.
- `tests/ui/run.mjs`: public CLI for existing/renamed UI inputs, ordinary helper
  JVM/host parity, parameterized UI branch preservation and source-linked negatives.
- `tests/integration/sdk.mjs <ui-evidence> <binary-backed.ets> <iterator-modules> <language-Iteration.ets> <stdlib-Iteration.ets>`:
  copies generated bytes unchanged into a fresh SDK host; builds all UI fixtures,
  consumes binary functions and cross-file iterators, checks actual compiler
  input records and HAP/ABC output. It never patches generated ETS.

The SDK test is a language/framework compilation check, not installation,
gesture testing or visual equivalence. Earlier page screenshots do not count as
evidence for this compiler revision. Final runs below used frozen production files.

## Remaining work

General dependency graph loading and KLIB inputs, broader generics/variance,
inheritance/interfaces/overloads/local classes, full collection and numeric
semantics, general coroutines and broader Compose/platform APIs remain separate
work. UI multi-file ownership for framework-generated component declarations is
not exposed by the current page CLI, although its output uses the shared program
representation. No compatibility adapter to the legacy Python page pipeline was
added.
